# Research Answers

## 1. How HTTP applications preserve state across request-response cycles

HTTP is stateless. This means the server retains no memory of previous requests and each request is treated as independent. Applications add state on top of the protocol, usually with sessions and cookies. When logging in, the server checks the user's credentials and creates a session record to hold their identity. It stores this on the server (e.g in a database, cache or signed cookie), and sends the browser a random session identifier in a Set-Cookie header. The browser returns that cookie with every subsequent request, so the server can look up the session and recognise the user. This is how authentication persists without asking for a password each time. Session management also covers expiry, renewal and logout (the session is deleted and the cookie cleared). For security purposes, cookies should be marked HttpOnly, Secure and SameSite, identifiers should be unpredictable, and the identifier should be regenerated at login to prevent session fixation. Django follows this pattern. Its session middleware attaches request.session to each request, its authentication system stores the user's ID in that session, and CSRF tokens protect the POST forms. Alternatives include token-based approaches such as JSON Web Tokens (useful for APIs).

## 2. Django database migrations to a server-based relational database such as MariaDB

To move from the default SQLite database to MariaDB, preparations need to be done on the server. A database is created with the utf8mb4 character set, and a dedicated user is given privileges on that database. On the Django/client side, a MySQL client library such as mysqlclient or similar is installed (Django's MySQL backend also supports MariaDB). In settings.py, the DATABASES setting is changed to use the engine django.db.backends.mysql, with the database name, user, password, host and port. These credentials should be stored in and retrieved from environment variables or a protected options file (not source control). Next, python manage.py makemigrations generates migration files from model changes, and python manage.py migrate applies them to the new database. This creates Django's own tables. Migrations are tracked in the django_migrations table, which ensures idempotence. Existing data can be exported from SQLite with dumpdata and loaded with loaddata after migrating. The application should be tested against MariaDB, and a backup should be taken before applying migrations to production.
